# database/

Database definitions for the AI-Driven Product Assistant backend: document structures,
validators and index definitions. **This package does not open connections.**
`backend/db.py` (`init_db`, `get_db`, `get_client`) stays the single source of the
MongoDB handle, and the handle is passed in to functions here.

```
database/
├── __init__.py        # exports create_indexes, INDEX_SPECS, validate, VALIDATORS
├── indexes.py         # create_indexes(db): centralised, idempotent index creation
└── schemas/
    ├── _validation.py # small shared validation helpers (no third-party deps)
    └── *_schema.py    # one module per collection: FIELDS, EXAMPLE, validate_*()
```

## Conventions

- Documents use **string ids** generated by `helpers.generate_id(prefix)` (e.g. `usr-…`),
  not ObjectIds. Relationships are string fields such as `userId -> users.id`.
  The only ObjectId is MongoDB's own `_id` (`chat_messages` is ordered by it).
- Timestamps are **ISO-8601 UTC strings** from `helpers.now_iso()`, not BSON dates.
- Validators return a list of error strings (empty = valid). Unknown fields are allowed.
- There is no `preferences` collection: preferences are embedded in `user_state`.

## Collections

| Collection | Written by | Key fields | References |
|---|---|---|---|
| `users` | auth | id, username, email, name, role, createdAt, passwordHash | n/a |
| `workspaces` | workspace, auth (seed) | id, userId, name, description, createdAt | userId -> users.id |
| `user_state` | auth, workspace, preferences | userId, activeWorkspaceId?, preferences{} | userId -> users.id; activeWorkspaceId -> workspaces.id (soft) |
| `themes` | auth (seed), theme | id, userId, name, keywords[], description | userId -> users.id |
| `feedback` | feedback | id, userId, title, message, customer, source, sentiment, theme, votes, createdAt | userId -> users.id |
| `features` | feature | id, userId, name, theme, reach, impact, confidence, effort, status, description | userId -> users.id |
| `prds` | prd | id, userId, title, featureId, version, status, createdAt, updatedAt, content | featureId -> features.id (soft) |
| `roadmap` | roadmap | id, userId, name, featureId, startDate, targetDate, priority, status, owner, theme | featureId -> features.id (soft) |
| `products` | product | id, userId?, name, description, category, status, tags[], attributes{}, createdAt, updatedAt | userId optional (shared catalog if absent) |
| `activity` | feature, feedback, prd, roadmap, workspace | id, userId, text, at | userId -> users.id |
| `chat_messages` | chat | userId + frontend-defined fields | userId -> users.id |

"Soft" references are not enforced or cleaned up by the routes. Full field lists,
rules and example documents are in each `schemas/*_schema.py`.

## Indexes

Created by `create_indexes(db)` (see `indexes.py` for the exact specs):

| Collection | Index | Serves |
|---|---|---|
| users | unique `id`; unique `email`; unique `username` (case-insensitive) | login / register lookups |
| workspaces, themes, features, prds, roadmap, feedback | unique `(userId, id)` | `find_one/update/delete {id, userId}` |
| feedback | `(userId, createdAt desc)` | list sorted newest first |
| user_state | unique `userId` | every read/upsert |
| products | unique `id`; `createdAt desc` | lookups by id; list sort |
| activity | `(userId, at desc)` | latest 50 events |
| chat_messages | `(userId, _id)` | history in insertion order |

`themes` uses a compound key because every user is seeded with the same theme ids.

## Initialisation

`create_indexes(get_db())` runs once at startup from `create_app()` right after
`init_db(app)`, unless `ENSURE_INDEXES` is set to `False` in the app config. It is
idempotent and safe on existing data:

- A **unique index is skipped with a warning** if existing documents already contain
  duplicates for that key (nothing is modified; clean the data, then restart).
- If MongoDB is unreachable it stops after the first failure and the app still starts.
- The result is returned as `{"ensured": [...], "skipped": [...], "failed": [...]}`.

Manual run from the `backend/` directory:

```python
from app import create_app
from db import get_db
from database import create_indexes
create_app({"ENSURE_INDEXES": False})
print(create_indexes(get_db()))
```

## Validation

```python
from database import validate
errors = validate("feedback", doc)   # [] when valid
```

Validators are not wired into the routes, so existing request and response behaviour is
unchanged. Call them from a route only where you want stricter checks.
